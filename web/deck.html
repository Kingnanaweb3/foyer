Why it matters

The blocker isn't capability. It's accountability.

Building an agent that answers questions is easy. Building one a nonprofit board will actually switch on is the harder problem — and AWS's own Public Sector guidance names why.

AWS names it

Turnover

Volunteers and staff rotate. The person who set the agent up may not be there in a year.

AWS names it

Board accountability

Someone has to answer for what the agent did, to people who have never touched it.

AWS names it

Unexplainable decisions

Agents whose reasoning can't be shown are the thing that stops adoption. This is the one Foyer is built around.

What we built

One agent. Two jobs. One of them it can't finish alone.

Front desk · acts alone

Answers, and actually does things

Event times, parking, remaining spots. Writes RSVPs straight to the roster and refuses when an event is full. These are small and reversible, so nobody's approval is needed.

Donor steward · always stops

Drafts, explains, waits

Measures each donor against their own giving rhythm, writes the re-engagement message — then queues it with its reasoning. It has no way to send.

The differentiator

The boundary is structural, not instructed.

Most guardrails are a sentence in a prompt asking the model to behave. Foyer's is a gap in the tool registry — there is nothing to reach for.

In the code

No send tool exists

The Donor Steward's registry holds draft_followup_message and queue_approval. There is no send. No prompt can talk it past a gate it cannot see.

In the code

Approve isn't a tool either

decide() is a plain function in governance/queue.py, deliberately not decorated. Only the web layer calls it — the agent cannot approve its own draft.

Both claims are verifiable in the repository in under a minute.

Architecture

Built on Strands Agents. Genuinely multi-agent.

Community member / donor

web chat

Foyer orchestrator

routes, never answers

Front Desk · Donor Steward

separate tool registries

Approval gate

human decides · then it sends

Agents as tools

Sub-agents are exposed to the orchestrator as callable tools, so routing is a logged decision rather than a keyword match.

Per-donor cadence

check_lapsing_donors compares each donor to their own giving rhythm — a first-time giver is never flagged, because there is no pattern to break.

Shared governance layer

Both sub-agents write to log_decision. Human approvals land in the same trail, so the record is one story.

Model-agnostic by design

Strands separates the agent from the provider. Swapping models is a single file — the tools, boundaries and logs are untouched.

What it isn't, yet

The limits, named. Before you find them.

Sample data, not a real organisation

Riverside Community Trust is fictional. The donors and events are sample records. The behaviour is real; the nonprofit isn't — no pilot has run yet.

Not deployed on AgentCore

The repo is AgentCore-ready — entry point and config are committed — but deployment fails on an account-level quota. A support case is open. Inference runs on a non-Bedrock provider for the same reason.

JSON store, not a database

Fine for a demo, wrong for real donor records. Durable storage is the first thing a pilot would need.

Email only, single organisation

SMS and WhatsApp are the intended delivery channels and aren't built. There's no multi-tenancy — one org per deployment.

Thesis

Restraint is the feature

The brief asked for agents that run quietly and only surface for a real decision. That isn't a limitation to engineer away — it's the thing that makes an agent adoptable by people who have to answer for it.
